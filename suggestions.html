Decision desk

Review the options, pick a path, then we build

This page is where the next version of this site gets decided. Nothing here is implemented until a reviewer marks a row Approve, Reject or Defer with a date. Each suggestion states the buyer problem it solves, the options with their trade-offs, the evidence it needs, and what it blocks. Suggestions SG-01 to SG-10 came from the first build and stand as written; SG-11 onward are added by this pass.

Three things to know before you read. (1) The site currently shows no price or rating figures on shop pages, because Amazon’s policies only allow a site to display price and availability when Amazon serves it or when it comes from the Creators/PA API, with caching capped at 24 hours — see FLG-021. (2) We have not cooked in any product, so no copy may imply we have. (3) Traffic, ranking and revenue are not forecasted anywhere on this site; the campaign ledger is empty by design.

Choose a path

If you approve a bundle, everything inside it moves together. Each bundle is a coherent story for the reader, not a random list.

Path A

Earn trust, then traffic

Ship the honest-shop polish: link-only pricing with better CTAs, a real comparison tool, the “what the listing does not say” boxes, and the review desk kept out of the reader’s way.

  • SG-11, SG-12, SG-13, SG-17, SG-21

Cost: mostly copy and one build. Needs no new accounts. Unblocks: nothing external, everything internal.

Path B

Get found, then write to what arrives

One canonical site, real Search Console data, per-page metadata, structured data, internal-link spine and a weekly cadence, so the next topic is chosen from queries rather than instinct.

  • SG-02, SG-14, SG-15, SG-18, SG-22, SG-24

Cost: low build work + owner access to Search Console and Associates Central. Needs ~4 weeks before data is meaningful.

Path C

Look like a magazine, not a spreadsheet

The visual overhaul: the design brief below, a typography and layout pass, real imagery only once a licence exists, and a voice pass over every article.

  • SG-16, SG-19, SG-20, SG-23, SG-25, SG-04

Cost: the highest design effort and the only path that can go wrong visually. Blocked by SG-04 (photography licence) for the imagery half.

Our recommendation, stated plainly: Path B first, then A, then the non-imagery half of C. The site’s data is already better than most affiliate sites’; its problem is that nobody has been shown it yet. Photography stays gated until SG-04 clears, because a licence problem is a bigger loss than a plain-looking page.

New suggestions from this pass

Each card is written so a decision can be made from it alone: what a buyer would feel, what the alternative costs, and what evidence has to arrive first.

SG-11 · Make “see today’s price” the primary button, everywhere

Buyer problem: a stale price on a review page is the fastest way to lose trust and the click. It is also the number a static build cannot keep true.

Option 1 (recommended): link-only pricing. Button reads “See today’s price on Amazon”; the register keeps the dated figure we observed.

Option 2: keep a dated snapshot with a visible “as of” chip and an automatic removal rule after N days.

Option 3: live figures only through the Creators/PA API (needs SG-12).

Effort: already implemented in this pass as Option 1 (one flag in data/editorial.json flips it). Evidence: Associates Program Policies on price/availability display and the 24-hour caching rule. Blocks: nothing. Status: Approve / reject the Option 1 default

SG-12 · Request Creators API access and build a refresh job — as a gate, not a promise

Why: it is the only compliant way to show live price, availability and images, and the only way “automation” stops being manual.

Option 1: apply once the account qualifies; a nightly job writes data/products.json fields with a timestamp; the build refuses to publish if the timestamp is older than 24 h.

Option 2: stay manual, and keep the “last checked” date visible on every page (what the site does now).

Blocked by: account eligibility. Third-party guides state API access follows three qualifying sales inside 180 days; we have not read that on an Amazon page in this session - see FLG-026. Evidence needed: Associates Central → Tools → Product Advertising / Creators API screen. Status: Owner action

SG-13 · Put “what the listing does not say” inside the buying flow, not in a footer

Buyer problem: the reason people leave an affiliate page is that it answers nothing they could not read on Amazon. The gaps in our own data are the most useful thing we have.

Option 1 (recommended): a per-product gap box (“wattage not shown in the fields we captured - check product details before you plan a circuit”), which is already on every card as Check before you buy.

Option 2: a single site-wide limitations note (weaker: readers skip it).

Effort: copy only. Risk: none - it is the truth. Status: Implemented in this pass

SG-14 · One site, one canonical, one sitemap

Why: the repository currently publishes three overlapping builds (root, counter-check/site/, and a pending docs/ draft). Search engines get three near-duplicate sites; readers get a brand split three ways.

Option 1 (recommended): root is the publication. Other builds become review-only: <meta name="robots" content="noindex, follow"> plus a banner naming the canonical, and removed from the sitemap.

Option 2: delete the duplicate builds at the next integration.

Option 3: keep them indexable (not advised).

Also in this pass: build_site.py used to write placeholder-domain canonicals into every page - the deployed HTML had been patched by hand, so the next rebuild would have re-broken them. Now every page self-canonicalises to its own URL, and the sitemap lists exactly the pages the build writes. FLG-024. Status: Owner: confirm the domain, then ratify Option 1 or 2

SG-15 · Fix the two metadata bugs that would have mattered most

Found, not guessed: (a) every page pointed its canonical at the home page while the sitemap listed the page itself - Google’s own guidance says do not declare different canonicals by different methods for the same page; (b) og:image was a relative SVG path, and social platforms need an absolute URL to a raster image, so no link ever rendered a card.

Fixed in this pass: per-page canonical, absolute og:image, a 1200×630 PNG brand card, per-page og:url, twitter: pair, and unique titles/descriptions on all pages. Remaining: verify in the Facebook debugger and X card validator after deploy (2 minutes, owner). Status: Implemented; needs owner verification

SG-16 · Run the anti-slop pass as a checklist, and keep it enforced by the build

Why: “looks like AI slop” is a concrete, fixable list: em-dash padding, “delve”, “in today’s fast-paced world”, unearned first-person testing, emoji as icons, symmetric card grids with no opinion, benefits without objects, and adjectives where a number should be.

Option 1 (recommended): the build fails if a banned phrase appears in a page; the list lives in data/editorial.json so writers can extend it.

Option 2: editorial guideline only (rots within a month).

Implemented: scripts/check_meta.mjs checks the banned-phrase list and the voice rules on every page. Status: Implemented in this pass

SG-17 · Make the mobile experience the default, not the afterthought

Buyer problem: this traffic is mobile. Two-finger zoom on a nine-column table and a 30-pixel tap target lose the click before the disclosure is even read.

Implemented in this pass: 44-48 px targets, a 16 px body floor, horizontal table scroll with a visible edge, sticky comparison bar, cards that stack without orphan columns, and a disclosure strip that stays legible at 320 px. Still needs: a real-device pass by the owner (we cannot screenshot a phone from here). Status: Owner spot-check on a phone

SG-18 · Decide the author byline now

Why it is a decision, not a task: every page needs a named responsibility. This site will not invent a person with credentials it cannot show.

Option 1: desk byline only (“The Countertop Guide editorial desk”) - honest, current, weaker on E-E-A-T.

Option 2: a named owner byline plus a real bio page and a contact address - strongest, needs a real person.

Option 3: commission a tester (SG-09) and byline them for tested content only.

Evidence needed: who is accountable for the claims. Blocks: any future “our expert” framing. Status: Needs decision

SG-19 · Publish the design brief as a single prompt (below), then rebuild once

Why: three sessions have each redesigned part of this site, which is exactly why it reads like a generated page. One brief, one pass, one reviewer.

Deliverable: the copy-paste prompt in the next section, written so a designer or a model can execute it without inventing claims. Status: Brief drafted in this pass; awaiting owner approval to execute

SG-20 · Kill the last audit-speak from reader pages

Problem: “verified fields only”, “FLG-0xx” and “snapshot” are the vocabulary of an internal register. A buyer wants “what to check”, “what this is good for”, “where it fits”.

Implemented: reader pages now lead with picks and checks; every register word moved to the review desk. The disclosure strip stays - it is required, and it is written in one sentence a person would say out loud. Status: Implemented; second opinion welcome

SG-21 · Add a “this vs that” pair page for the two real rivalries

Buyer problem: the highest-intent queries are comparisons of two things: dual-basket vs single basket, instant-read vs wireless. One page per pair, with a verdict-shaped summary that stays inside the specs.

Effort: two pages, no new data (all fields exist in the register). Evidence needed: none beyond re-reading the two listings on publish day. Status: Proposed

SG-22 · Turn the four blank spec cells into a tracked task list, then into content

Why: missing dimensions for both thermometers and missing wattage for the Emeril are the only blanks in the comparison. Each one blocks a whole class of question (“will it fit?”, “can two run on one circuit?”).

How to discover: re-read each listing’s product-details block, save the URL and the date, and only then write the fit guide. If the field is genuinely absent, the guide says so - which is itself useful. Status: Owner-adjacent: needs a listing re-read at publish time

SG-23 · Replace generic hero space with a single, ownable visual

Problem: with no product photography permitted, the site needs one strong non-product visual identity (a measured counter-depth diagram, a spec-dial, a typographic masthead) so a reader remembers it without a single food shot.

Option 1 (recommended): a drawn counter-depth scale comparing 32.4 / 34.0 / 42.9 cm, built from our own derived numbers - original, useful, and impossible to mistake for stock.

Option 2: photography after SG-04.

Effort: one SVG + a component. Risk: must stay clearly labelled as a diagram, not a photo of the product. Status: Proposed

SG-24 · Measure before optimising: 28 days of Search Console, then pick topics

Why: the brief’s own priority. The queue in data/editorial.json is a stated plan; after 28 days of queries, the next four topics come from queries that arrive and that our pages do not answer.

Needed from owner: Search Console property verified for the chosen domain, and permission to record which queries we act on in the ledger. Status: Blocked on SG-02

SG-25 · Keep the compliance gate in CI, and let it fail the deploy

Why: a rule only holds if a build breaks when it is missed. The deploy workflow now runs the generator, then a checker, before uploading - disclosure, sponsored marking, per-page metadata, link integrity, price policy and banned phrases.

Implemented: scripts/check_meta.mjs wired into .github/workflows/pages.yml as a blocking step (this also closes request R-01 from session b4c6c619). Status: Implemented; watch the next deploy

The design brief - copy-paste prompt

Copy the block below into a design tool or a designer’s brief. It is written so that nothing in it can be executed by inventing a fact: the visual layer may change, the evidence layer may not. Items marked [owner] must be filled before the work starts.

 redesign The Countertop Guide - a spec-backed Amazon affiliate publication for
air fryers and meat thermometers. Single-file static HTML built by build_site.py from
data/products.json (specs, sources) and data/editorial.json (voice, display policy,
cadence). Deployed by GitHub Pages. Tracking ID [owner-confirmed]: shopnow047c-20.

GOAL
Make it read like a specialist shop window, not a compliance audit. A buyer who has
never heard of us should, in 15 seconds, understand: what we sell nothing of, what
each product is genuinely good for, what to check before ordering, and that we are
paid if they click. Trust is the conversion mechanism here - we win by being the page
that admits what it does not know.

READER
US kitchen-appliance shopper, mobile-first, mid-funnel, comparison-ready. They have
already seen the Amazon listing. They arrive from a typed question ("does a 6-quart
dual basket feed 4", "instant read vs wireless thermometer accuracy"). They leave when
a page says "we tested" without evidence, or shows a price that is wrong.

BRAND [owner]
Name: The Countertop Guide (settled in D-18 of the external register; reopen only with
a reason). Voice: plain-spoken buying desk. Second person, active, one idea per
sentence, numbers instead of adjectives. Reading age ~grade 8. Never cute about safety
or money.

LAYOUT / RHYTHM
1. Masthead: wordmark + reader nav (Air fryers, Thermometers, Compare, Guides, About)
   + one "Review desk" group for every internal/admin surface.
2. Disclosure strip immediately under the masthead, on every page, one line, legible,
   not hidden in grey-on-grey. Repeat in the footer.
3. Front page order: hero question -> quick picks -> product cards -> chooser ->
   guides -> the short "why the numbers match" trust block. Products before process.
4. Category page: one-line lede -> shortlist callout -> product cards -> spec table ->
   related guides.
5. Product card: form-factor chip, name, one-line job, spec grid (capacity as titled,
   footprint, depth, care per listing), "Good for", "Check before you buy", primary CTA
   "See today's price on Amazon", then one quiet line: sponsored, opens Amazon, source.
6. Comparison: sticky bottom bar on mobile, horizontal-scroll table with a visible edge,
   first column frozen, derived rows visually marked as derived.
7. Guides: single column, max 68ch, drop-cap-free, no centred hero, question H2s,
   "what the listing does not say" box, a next step at the end.

TYPE / COLOR
Warm paper background, near-black ink, one saturated accent (burnt orange) used ONLY
for actions, one teal for informational accents. Serif or high-contrast sans for
headlines (max 2 families), system-usable body face. 16px body minimum, 1.6 line,
32/24/20px H1/H2/H3 on mobile, larger on desktop, no fluid type below 320px.
Contrast >= 4.5:1 body text, 3:1 large. Radius 14-18px, one shadow level, hairline
borders - no glassmorphism, no gradient text, no glow, no oversized rounded pills.

IMAGERY [owner - blocked]
No Amazon images, no scraped photography, no AI-generated product or food images:
Program Content includes data, images and text and the IP License caps caching of
product images at 24 hours. Until a licence or in-house shoot exists (SG-04), use
original diagrams only (counter-depth scale, capacity-per-footprint chart), clearly
labelled as our drawings. If a reviewer approves photography, real photos only,
credited, with the shoot date on the page.

COMPONENTS
Chip, product card, spec dl, callout, decision-card, comparison table, chooser form,
details/summary FAQ, badge-ok / badge-warn / badge-flag, source footnote row. Tap
targets >= 44px. Every table gets a scroll wrapper. Print stylesheet for the
comparison page.

NON-NEGOTIABLE RULES (the build must refuse to publish without them)
- Every outbound product link: rel="sponsored nofollow noopener", visible "sponsored"
  word, destination never obscured, tag parameter on the URL only.
- Disclosure: the Associates statement exactly as the Operating Agreement Section 5
  requires it, plus a plain-language line. Above the fold and in the footer.
- No price or rating figures on shop pages unless a Creators/PA API refresh exists;
  never a figure older than 24h. (Participation Requirements + IP License clause (h).)
- No "we tested/we tried/we loved", no superlatives, no scarcity, no countdowns,
  no invented expert quotes. Banned-phrase list in data/editorial.json is enforced.
- Every product fact links to the listing it came from; a missing field is stated as
  missing, never inferred.
- Unique <title> + meta description per page; self-referencing canonical; absolute
  og:image (raster); sitemap lists exactly the pages the build writes.
- No third-party trackers. Five first-party events only, local by default.

WHAT "DONE" LOOKS LIKE
A buyer can screenshot one product card and their partner understands the trade-off
without visiting Amazon. Nobody reading the page could tell it was generated, because
it says specific things, admits its gaps, and never asks to be believed.
