Method

How we verify, measure, and decide - without hallucinating

Automate what can be automated; put a gate in front of what cannot. This page is the machinery: evidence rules, analytics events, and the empty campaign ledger.

Evidence rule

  • Every product fact links to its Amazon listing and verification record. Missing = blank + flagged.
  • "Trending" / popularity claims require a dated snapshot from an official category page. We make none.
  • Seller claims are attributed ("per listing"). Derived math shows its method. Prices always carry a snapshot date.
  • Hands-on testing claims require a published protocol and photos. We make none.

Analytics: five defined events (privacy-preserving)

Implementation: one client, assets/app.js, and those five names only. It counts in localStorage and beacons to a configurable endpoint (data-analytics-endpoint) that is empty in this build, so nothing leaves the browser. No cookies, no identifiers, no third-party trackers.

Contract notes settled in this pass: two other tracker scripts exist in the repository (app.js at the root, serving the articles/ and docs/ build, and assets/js/analytics.js, unreferenced). They use different event names and payloads from the server stub in analytics-endpoint/. This session did not edit those files - they belong to other sessions - and instead records the single taxonomy above as the one the root site uses. Unifying the rest is SG-03; see also FLG-034 for the sponsored-marking fix in the chooser output.

Endpoint status, stated exactly: no host is configured, so nothing is transmitted. The endpoint implementation in this repository (analytics-endpoint/server.py, owned by another session) accepts a payload carrying event, path and an optional asin and knows three of these five names (page_view, outbound_click, and its own guide_read_75 for the 75% scroll event). The client here sends a payload that satisfies that validator today, and keeps the five names above as this site’s contract. Checked by running the endpoint’s own validator against our payload in this session: page_view and outbound_click return valid, the other three names return “unknown event”. Reconciling that vocabulary is request R-06 in COORDINATION.md - the endpoint is owned by another session, so it was not edited here.

What is automated, and what is gated

StepStateHow it works / what stops it
Page renderingAutomatedbuild_site.py writes every page, the sitemap, the feed, robots and the search index from data/products.json + data/editorial.json. No page is hand-edited, and the build is deterministic: the same data produces the same files, so a CI diff catches a stale commit.
Metadata, disclosure, sponsored marking, voice rulesAutomated + blockingscripts/check_meta.mjs runs in the deploy workflow after the build. A duplicate title, a missing canonical, an unlabelled Amazon link, a broken internal link, a banned phrase or a price figure on a shop page fails the deploy.
Adding a guide to sitemap and feedAutomatedThe guide list and the page registry drive both files, so a new guide cannot be published and forgotten.
Product data refreshGatedManual re-read only. Creators/PA API access is the automated route and is not available to this build yet (FLG-037).
Publishing pathSplit todayThe workflow builds, checks determinism and runs both gates on every push to main; the pages readers see are served by GitHub’s branch build, because that is what the repository’s Pages source is set to. A gate failure therefore marks the commit red instead of stopping a publish. Switching the build source to GitHub Actions would make the gate block the deploy (SG-43, FLG-051).
Special Link validationGatedA human must click a test link in the enrolled Associates workflow and confirm the destination and the tracking report (SG-01). No automation can substitute for it.
Conversion and revenueGatedFilled only from authorized first-party reports; nothing client-side may write a conversion.
PhotographyGatedLicence decision pending (SG-04, FLG-038).
